# Decision register

**Status vocabulary**
- **Confirmed:** user accepted the product/operating decision.
- **Provisional:** intended direction, but requires technical validation or later approval.
- **Open:** not decided; agent must ask or propose options.
- **Deferred:** intentionally moved to a later stage.
- **Out of scope:** excluded from current roadmap.

## Confirmed product decisions
- Mobile-first responsive web app, usable on phone/tablet/desktop.
- One group shown in V1 UI; multi-group-ready data model with `group_id` isolation.
- Doubles only, one court, one match at a time.
- Score: at least 21, lead by 2, maximum 30; no point-by-point tracking.
- One authorised controller at a time; handover/takeover logged.
- Select four distinct players, assign visible Team A/B slots, enter two scores, save.
- Score validation immediate and server-side; save retries idempotent.
- 10-second immediate Undo only for original recorder; undo is audited and voids/reverses result.
- Later corrections are authorised and reasoned; corrections trigger deterministic recalculation.
- One active session per group; session is manually started and ended.
- Attendance is separate from match participation; late arrivals can be added.
- Session date/time uses `Asia/Kuala_Lumpur`; store timestamps consistently in UTC where appropriate; display `DD MMM YYYY`.
- Membership invitation-only, email-bound, single-use, expires after 7 days, revocable; invitation does not grant access until authentication/verification and admin approval.
- Individual accounts; email/password with verification and Google sign-in. Google login alone does not grant membership.
- Roles: member, authorised recorder, admin, owner; recorder permissions explicit.
- Owner/admin manage permanent roster and identity merges; recorder can add temporary guests.
- Player identity separate from account; duplicate names allowed; never merge by name alone.
- Returning member profile relinking requires admin verification.
- Member may be approved as viewer without player profile; unconfirmed profiles cannot play official matches.
- Temporary unmerged guests appear in the all-time leaderboard with a visible `Guest` label; merging a guest into a permanent player profile preserves audit history and triggers deterministic rating recalculation.
- Invitation links in V1 are generated by owner/admins and copied/shared manually; server-side RPCs enforce verified email matching (`lower(trim(email))`), single-use redemption, 7-day expiry, revocation, and subsequent admin approval.
- Prefer Google sign-in for convenient initial V1 onboarding (avoids Supabase built-in SMTP 2 emails/hour rate limit); if email/password authentication is used, document verification/reset rate limits and custom SMTP requirements before pilot launch.
- Members can dispute any match; one open dispute per match; reasoned resolution; notify recorder and admins (Stage 2 UI; Stage 1 preserves replay invariant that disputed matches remain official until resolved).
- In-app notifications only in V1; no email/browser push (Stage 2 notification centre UI).
- All-time leaderboard primarily by Elo; seasonal and session rankings separate (Seasons UI deferred to Stage 2; Stage 1 `sessions.season_id` is nullable and defaults to `NULL`).
- Display `before` and `after` ratings as rounded whole numbers and rating `change` (`delta`) to one decimal place; explicitly explain in the UI that displayed values are rounded independently from internal decimals.
- Use consistent exact `NUMERIC(10,4)` fixed-point precision and half-away-from-zero rounding at the 4th decimal place across PostgreSQL and TypeScript domain logic.
- Global chronological match ordering for deterministic replay is fixed to `(sessions.session_started_at ASC, sessions.created_at ASC, sessions.id ASC, matches.sequence_number ASC)`.
- Per-session `sequence_number` is assigned at match completion and is strictly immutable (never reused or inserted into). In Stage 1, forgotten matches added to a reopened session are appended at the end (`MAX(sequence_number) + 1`).
- Creating a backdated session dated before an existing session containing rated matches requires Admin/Owner authorization and displays a warning that historical ratings may be recalculated.
- Session start time defaults automatically to current time (`now()`) upon session creation. The manual Start Time editing UI and Start Session datetime input have been removed from the client interface to eliminate courtside recording friction; the server-side RPC (`public.update_session_start_time`) is preserved for backend administrative and data integrity needs (Policy 3B UI Streamlining).
- Distinguish `Current`, `Recalculating`, and `Stale/Failed` rating states on leaderboard and profile views using `groups.required_match_state_seq` and `groups.published_rating_version_id`; never claim stale published ratings reflect the latest match history when recalculation is pending or failed.
- Session ranking: wins, then win rate, then point difference; exact ties share rank. Show sample sizes.
- Attendance rate = attended sessions / sessions held since profile creation; attendance is not match participation.
- Session point difference counts a player's team points minus conceded points across completed matches.
- Inactive status manually managed; does not change ratings.
- Completed sessions locked by default; reopening is authorised, reasoned, and audited.
- Corrections have no fixed time limit, but require authorisation and reason.
- Current session standings are provisional until finalization.
- Session finalization requires all unfinished matches completed or explicitly voided.
- Abandoned-session warning after 12 hours since meaningful activity; never auto-close.
- Match history filters by session/date, player, status; newest first.
- Copyable WhatsApp session summary after finalization and for older sessions; no shareable image in V1 (Stage 2).
- Dark theme only; defaulted and locked to dark theme; manual theme switching and light theme removed per owner directive; English V1.
- Optional avatar; no unnecessary personal data; emails private.
- Basic PWA install support, no offline recording or browser push (Stage 2 polish).
- CSV historical import is optional admin-only, preview/validate entire batch, atomic commit; no raw Notes/WhatsApp parser in V1 (Stage 2).
- Private GitHub repo initially; free Vercel URL; custom domain later if useful.
- Stack confirmed for V1: React + TypeScript + Vite frontend, Supabase PostgreSQL/Auth/Realtime, Vercel frontend hosting; no custom Express backend in V1.
- Bootstrap must securely establish one owner/group and then disable itself; no reusable secret in browser.
- Provider backup initially, but verified free-tier limitations require CLI/logical dump runbook (`supabase db dump`) because automated daily backups and PITR are paid Supabase features; user-facing export not required in V1.
- Data deletion/account anonymisation must explain historical retention and follow applicable privacy requirements.
- Guided coding workflow; phase plan approval required before each implementation phase.
- Controlled command execution; approval for destructive/system-level commands.
- Phase-based Git commits; ask before pushing, force-pushing, or rewriting history.
- Explicit approval for production deployments/migrations/data operations/secrets/policies and recurring costs.
- Maintainable docs, phase reports, verified completion criteria.
- Risk-based ambiguity handling; stop-and-resolve conflicts; decision register.
- Design-system-first, browser-verified where available, milestone UI reviews.
- Technical research from official docs for changing facts; cite verification date/source.
- Build in three stages; features must be labelled included/deferred/out-of-scope.
- Progressive context; prompts self-contained but canonical docs remain source of truth.
- Rationale recorded for critical decisions only.
- Existing repository inspection and preservation required before edits.
- Antigravity is the target harness; core documentation remains portable.

## Provisional technical decisions
- **Rating method:** doubles Elo using average team ratings and outcome-only updates; score margin has no effect.
- **K-factor (`DEC-009` — Initial Pilot Default Approved):** `K = 24` is approved as the **initial pilot default**, not as permanently validated production behaviour. `k_factor` and `rules_version` must remain configurable and recorded on every `rating_versions` row. Before wider production rollout, the synthetic simulation must be extended across multiple random seeds and varied attendance, skill, partnership, and upset scenarios.
- **Rating baseline:** 1000 (`1000.0000` internal `NUMERIC(10,4)`); whole-number display for before/after and 1-decimal display for rating change.
- **Provisional rating label:** until 3 eligible completed matches. This is a label threshold, not proof of reliability.
- **Physical schema & Phase 1 security safeguards:** Approved for local Phase 1 implementation with mandatory safeguards:
  - Store only cryptographic SHA-256 hashes (`token_hash`) of high-entropy invitation tokens; never persist or log raw tokens.
  - Use `SET search_path = ''` with fully schema-qualified object references on all `SECURITY DEFINER` functions, plus explicit function ownership and `EXECUTE` grants for intended roles only.
  - Enforce default-deny RLS across all tables, protect member emails and invitations from unauthorized access, and require atomic, audited transactions for ownership transfer, invitation redemption, membership decisions, and explicit UUID-based profile linking.

## Open decisions / validation tasks
- Extend synthetic Elo simulation across multiple random seeds and varied attendance, skill, partnership, and upset scenarios before wider production rollout beyond the initial pilot.
- Review Phase 1 local database migration and automated RLS/security test evidence before approving Phase 2.
- Decide any technical detail that affects privacy, security, data integrity, costs, or user-visible behaviour through explicit proposal/approval.
- If requirements conflict or evidence shows a requirement is unsafe/impossible, stop affected work and ask the owner.

## Change control
When a material decision changes:
1. Record old and new decision, rationale, date, approving actor, affected files and migration implications.
2. Update canonical requirements and traceability.
3. Identify tests that must change.
4. Never let a prompt silently override this register.
